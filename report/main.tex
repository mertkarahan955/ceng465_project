\section{Introduction}
% ═══════════════════════════════════════════════════════════════════════════════════

This project implements single-leader replication on two physical macOS machines over a
LAN, using MongoDB as the storage engine and a Python/Flask control node as the client.
Every write is tracked from the moment PRIMARY commits it to the moment SECONDARY applies
it, with the replication delay recorded in an application-level operation log.

The domain is a \textit{fleet management system} with six collections: vehicles, drivers,
depots, shipments, GPS positions, and incidents. Each collection has a different write
frequency and consistency requirement, making the domain a natural fit for demonstrating
multiple consistency models with realistic data shapes.

The main goals of the project are:

\begin{enumerate}
  \item Deploy a two-node MongoDB replica set (\code{rs0}) on real hardware with no
        containers or simulated latency.
  \item Implement two replication modes --- synchronous (PRIMARY waits for SECONDARY ACK)
        and asynchronous (PRIMARY returns immediately) --- with a measurable operation log
        that records \code{leader\_write\_time}, \code{follower\_visible\_time}, and
        \code{replication\_delay\_ms} per write.
  \item Demonstrate five consistency scenarios via interactive DDIA-style timeline
        diagrams on an experiment dashboard.
\end{enumerate}

\subsection{Replica Set Configuration}

The secondary is configured as a non-voting, zero-priority member (\code{votes=0},
\code{priority=0}). This keeps the primary always writable regardless of secondary
availability, at the cost of disabling automatic failover. The trade-off is acceptable
for a two-node demo environment where observing replication behaviour is the goal.

The system supports two replication modes controlled via MongoDB's write concern
parameter: \textbf{synchronous replication} (\code{w=majority}), where PRIMARY waits
for SECONDARY to acknowledge before returning success, and \textbf{asynchronous
replication} (\code{w=1}), where PRIMARY returns immediately after its own write without
waiting for the secondary. For synchronous writes, the application pings the secondary
\textit{before} issuing the primary mutation. If the secondary is unreachable, the write
is rejected immediately with a clear error instead of blocking until the MongoDB
wire-level timeout fires.

Two daemon threads run for the lifetime of the Flask process: a \textbf{reconciler} that
fires every second to close pending log entries once the secondary's document version
catches up, and a \textbf{health-check loop} that detects secondary recovery and drains
any accumulated pending entries via batch reconciliation.

\subsection{Document Envelope}

All six fleet collections share a common schema envelope. Every document carries the
fields listed in Table~\ref{tab:envelope}; domain-specific data lives in the nested
\code{value} object.

\begin{table}[H]
  \centering
  \caption{Common document envelope (all fleet collections)}
  \label{tab:envelope}
  \small
  \begin{tabularx}{\textwidth}{llX}
    \toprule
    Field & Type & Purpose \\
    \midrule
    \code{\_id}               & ObjectId  & MongoDB primary key \\
    \code{key}                & string    & Domain identifier (e.g.\ \texttt{VHC-001}, \texttt{INC-TRK-42}) \\
    \code{value}              & object    & Nested domain payload (varies per collection) \\
    \code{version}            & integer   & Starts at 1; incremented on every write \\
    \code{leader\_term}       & integer   & Monotonically increasing leader epoch \\
    \code{last\_log\_index}   & integer   & Foreign key into \code{operation\_logs} \\
    \code{last\_operation\_id}& string    & UUID of the last mutation \\
    \code{last\_updated}      & datetime  & UTC timestamp of last write \\
    \code{deleted}            & boolean   & Soft-delete flag (no physical removal) \\
    \bottomrule
  \end{tabularx}
\end{table}

The \code{version} field is the primary reconciliation key: when the background
reconciler checks whether a pending log entry can be closed, it compares the secondary's
\code{version} against the \code{version\_after} stored in the log. If
$\text{secondary.version} \geq \text{version\_after}$, replication is confirmed and
\code{replication\_delay\_ms} is computed as
$(\text{follower\_visible\_time} - \text{leader\_write\_time}) \times 1000$.

\noindent\textbf{Rationale.}
Vehicles, drivers, and depots change rarely; stale reads are acceptable.
Shipment status must never appear to go backwards (\texttt{delivered} cannot revert to
\texttt{pending}), so monotonic reads are required. GPS positions are high-frequency but
a few seconds of lag is fine for fleet overview. Incidents are safety-critical: a
dispatcher who files a breakdown report must see it immediately, so reads are always
routed to PRIMARY.

Each collection has compound indexes tailored to its dominant access pattern. For
example, \code{positions} has an index on \texttt{(value.vehicle\_id, last\_updated
DESC)} for latest-ping queries, and \code{incidents} has an index on
\texttt{(value.resolved, value.severity)} for the safety dashboard.

\section{Logging Mechanism}
% ═══════════════════════════════════════════════════════════════════════════════════

Every insert, update, and delete produces exactly one entry in \code{operation\_logs}.
Table~\ref{tab:oplog} shows the schema.

\begin{table}[H]
  \centering
  \caption{\texttt{operation\_logs} document schema}
  \label{tab:oplog}
  \small
  \begin{tabularx}{\textwidth}{llX}
    \toprule
    Field & Type & Description \\
    \midrule
    \code{log\_index}              & integer  & Global monotonic counter (Raft-style log index) \\
    \code{operation\_type}         & string   & \texttt{insert} / \texttt{update} / \texttt{delete} \\
    \code{target\_collection}      & string   & Which fleet collection was mutated \\
    \code{target\_id}              & ObjectId & Affected document \\
    \code{leader\_write\_time}     & datetime & UTC -- when PRIMARY committed \\
    \code{follower\_visible\_time} & datetime & UTC -- when SECONDARY showed \texttt{version\_after} (null initially) \\
    \code{replication\_delay\_ms}  & float    & \texttt{follower\_visible\_time} -- \texttt{leader\_write\_time} (ms) \\
    \code{version\_before}         & integer  & Document version before the mutation \\
    \code{version\_after}          & integer  & Document version after the mutation \\
    \code{write\_concern}          & string   & \texttt{majority} or \texttt{1} \\
    \code{status}                  & string   & \texttt{pending\_follower} / \texttt{visible\_on\_follower} / \texttt{timeout} \\
    \bottomrule
  \end{tabularx}
\end{table}

A log entry starts as \code{pending\_follower}. For synchronous writes the application
polls the secondary inline (up to 5\,s at 10\,ms intervals) and closes the entry before
returning the HTTP response. For asynchronous writes the entry stays pending and is
closed by the background reconciler once it detects that the secondary's \code{version}
has caught up. If the secondary does not catch up within the poll window
the entry transitions to \code{timeout} and the reconciler retries on the next cycle.

\section{Experiments}
% ═══════════════════════════════════════════════════════════════════════════════════

The Flask dashboard at \url{http://localhost:5001/experiments} provides five runnable
experiments. Each produces a DDIA-style communication timeline and saves the full event
trace as a JSON file under \code{experiment\_results/<name>/}. Time flows left-to-right;
diagonal arrows show inter-node messages labelled with version information and latency.

% ─────────────────────────────────────────────────────────────────────────────────
\subsection{Experiment 1 --- Synchronous Replication}
% ─────────────────────────────────────────────────────────────────────────────────

A GPS position is written to PRIMARY using synchronous replication (\code{w=majority}).
MongoDB does not return \code{ok} until SECONDARY has replayed the oplog entry and
acknowledged. The client receives the response only after the full round-trip completes.

\textbf{Key observation:} The PRIMARY lane in the timeline shows a wide processing band
($\approx$160\,ms) blocked on SECONDARY's ACK before the client receives \code{ok}. This
directly visualises the synchronous replication penalty --- the price of durability ---
and shows that the dominant cost is SECONDARY's oplog replay and disk acknowledgement,
not the network hop itself (each one-way network leg is under 4\,ms).

\begin{table}[H]
  \centering
  \caption{Synchronous Replication --- representative run (\code{log\_index} 727, \code{operation\_id} c758eb2e)}
  \begin{tabular}{lrl}
    \toprule
    Metric & Value & Notes \\
    \midrule
    Total write duration       & 166.35\,ms     & Client $\to$ PRIMARY $\to$ SECONDARY $\to$ client (full round trip) \\
    Network: Primary $\to$ Secondary & 2.76\,ms & One-way oplog transmission \\
    SECONDARY apply + ACK      & $\approx$159.8\,ms & Dominant cost --- oplog replay \& journal fsync, not network \\
    Network: Secondary $\to$ Primary & 3.17\,ms & ACK transmitted back to PRIMARY \\
    Stale reads possible       & No             & \code{version\_after = 1} on both nodes before client receives \code{ok} \\

\subsection{Experiment 2 --- Eventual Consistency (Asynchronous + Artificial Delay)}
% ─────────────────────────────────────────────────────────────────────────────────

The replica set is reconfigured with \code{secondaryDelaySecs=1} to make the
inconsistency window observable. An asynchronous update (v1 $\to$ v2) is then issued;
\code{ok} returns without waiting for the secondary. Three secondary reads follow at
$\approx$330\,ms, $\approx$680\,ms, and $\approx$1281\,ms from experiment start.

\textbf{Key observation:} The first two reads return stale data (v1); only the third,
after the artificial delay expires, returns v2. The timeline shows red arrows for stale
responses and a green arrow when the nodes finally converge.

\subsection{Experiment 3 --- Read-After-Write}
% ─────────────────────────────────────────────────────────────────────────────────

A critical incident is inserted asynchronously. Two reads are issued immediately afterward:
one to PRIMARY (the correct path for the writing session) and one to SECONDARY (the
wrong path, where the oplog may not have arrived yet).

\textbf{Key observation:} The PRIMARY read is always fresh --- the incident is visible
within 1.11\,ms. The SECONDARY read may return nothing if the oplog has not yet arrived,
demonstrating the Read-After-Write anomaly and why safety-critical data in the
\code{incidents} collection is always read from PRIMARY.

% ─────────────────────────────────────────────────────────────────────────────────
\subsection{Experiment 4 --- Monotonic Reads}
% ─────────────────────────────────────────────────────────────────────────────────

A shipment document is written five times asynchronously, advancing its status from
\code{pending} to \code{delivered} (v1 through v5). After all writes complete on
PRIMARY, five sequential reads are issued to the \textit{same} SECONDARY and the version
sequence is checked for monotonicity.

\textbf{Key observation:} On a fast LAN the secondary catches up before the first read
is issued, so all five reads return v5. The version sequence [5, 5, 5, 5, 5] is strictly
non-decreasing --- the monotonic guarantee holds. The guarantee would still hold on a
slower link where earlier reads might return lower versions, because a single oplog
stream can never apply entries out of order.

\subsection{Experiment 5 --- Concurrent Writes: Propagation Order}
% ─────────────────────────────────────────────────────────────────────────────────

Two threads (User A and User B) each fire three asynchronous vehicle inserts simultaneously.
PRIMARY serialises all six writes and assigns sequential \code{log\_index} values.
After the burst, a snapshot read from SECONDARY verifies that all six documents are
present and in the same log-index order that PRIMARY assigned.

\textbf{Key observation:} The \code{log\_index} sequence [696--701] assigned by PRIMARY
is reproduced exactly on SECONDARY. Because MongoDB's oplog is an append-only log
applied in order, it is impossible for a document with \code{log\_index=698} to appear
before \code{log\_index=697}.

against the live replica set. All fleet collections are dropped and recreated at the

\subsection{Manual Secondary Failure Test}

The following sequence was executed manually to validate the write guard and catch-up
detection:

\begin{enumerate}
  \item Secondary machine taken offline (network unplugged).
  \item Synchronous write attempted $\to$ rejected immediately; no primary mutation.
  \item Replication mode switched to asynchronous.
  \item Insert succeeds on PRIMARY; log status = \code{pending\_follower}.

% ═══════════════════════════════════════════════════════════════════════════════════
\section{Discussion}
% ═══════════════════════════════════════════════════════════════════════════════════

\textbf{Durability vs.\ availability.}
Synchronous replication guarantees that a committed write survives a primary crash because
SECONDARY has already acknowledged it. The cost is $\approx$62\,ms latency and
unavailability while the secondary is unreachable. Asynchronous replication always
succeeds on the primary but risks data
loss if the primary crashes before the oplog propagates, and produces temporary stale
reads on the secondary.

\textbf{Consistency anomalies on a fast LAN.}
Our LAN produces sub-5\,ms RTTs, so the secondary typically syncs within 10--15\,ms of
an asynchronous write. Stale reads are difficult to observe without the artificial
\code{secondaryDelaySecs} setting used in Experiment 2. Real deployments across data
centres would exhibit these anomalies naturally.

\textbf{Why monotonicity holds.}
MongoDB's oplog is a strictly ordered, append-only log. A secondary applies entries in
log-index order, so a document's version can only increase on the secondary. Reading
from a single fixed replica therefore guarantees monotonic reads by design.

\textbf{Limitations.}
A two-node, non-voting secondary disables automatic failover. A three-node set with an
arbiter would enable re-election. Additionally, our application-level \code{operation\_logs}
duplicates information already in MongoDB's native oplog; a production system would use
change streams instead of polling.

% ═══════════════════════════════════════════════════════════════════════════════════
\section{Conclusion}
% ═══════════════════════════════════════════════════════════════════════════════════

This project implemented a complete single-leader replication system on real hardware and
demonstrated five consistency scenarios across two write concern modes:

\begin{enumerate}
  \item \textbf{Synchronous Replication:} 62\,ms total write; both nodes consistent
        before the client receives \code{ok}.
  \item \textbf{Eventual Consistency (asynchronous):} writes return in $<$10\,ms; secondary
        serves stale data for up to 1281\,ms when an artificial delay is in place.
  \item \textbf{Read-After-Write:} routing reads to PRIMARY for the writing session
        guarantees the writer always sees their own write (1.11\,ms read latency).
  \item \textbf{Monotonic Reads:} pinning reads to the same secondary ensures version
        numbers never decrease, regardless of replication lag.
  \item \textbf{Concurrent Writes:} the primary serialises concurrent writes via the
        oplog; the secondary preserves this order exactly.
\end{enumerate}

The application-level operation log (\code{operation\_logs}) provides full observability:
every write is tracked from \code{leader\_write\_time} through
\code{follower\_visible\_time}, making replication delay a first-class measured metric.
The six-collection fleet domain maps each collection to a distinct consistency model,
showing how a single replica set can serve both safety-critical (read-after-write on
incidents) and eventually-consistent (GPS heatmap on positions) workloads simultaneously.
